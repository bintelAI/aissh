# 前端数据迁移至本机 SQLite 存储推进方案

> 结论：当前项目的主要用户配置确实存放在浏览器/Electron 渲染进程的 `localStorage` 中。清理站点数据会导致其丢失。项目是本地化桌面软件，应由随应用启动的 NestJS 本地后端负责 SQLite 持久化，而非依赖远程 PostgreSQL 或登录服务。数据库必须放在应用用户数据目录，不能放在 `.app` 安装包、`resources` 或项目工作目录。

## 1. 目标与边界

**目标**：服务器资产、目录、命令模板、提示词等配置由本机 SQLite 保存。清理浏览器缓存、刷新界面、关闭重开和 macOS 覆盖安装后，数据仍可恢复。

**本机持久化边界**：

- 数据库存放在 Electron 的 `app.getPath('userData')/data/aissh.sqlite`。macOS 的实际路径位于当前用户 `~/Library/Application Support/` 下的应用数据目录；由主进程通过 `APP_DATA_DIR` 环境变量传给 NestJS 子进程。
- `.app` 的覆盖安装、浏览器 `localStorage` 清理和项目代码重新构建不会删除该目录，因此不会影响 SQLite 数据库。
- 用户手动删除应用数据目录、使用清理工具删除该目录，或在 Windows 卸载时启用删除应用数据，都会删除本地数据库。为覆盖该场景，必须提供自动备份和用户选择路径的导出/导入；没有云同步，就无法承诺跨电脑或“清空全部应用数据”后仍自动恢复。

**不在本期迁移范围**：活动 SSH 连接、终端滚动内容、连接状态、失败计数、临时会话、文件编辑中的未保存内容、当前批量对比结果。这些均为运行期状态，刷新后本就无有效的可恢复连接上下文。

## 2. 当前事实盘点

### 2.1 已由前端持久化的数据

| 本地键/来源 | 数据 | 现状与风险 | 本机后端处理建议 |
| --- | --- | --- | --- |
| `ssh_servers` | 服务器名称、IP、端口、用户名、目录及可选 `password` | `useSSHStore.ts` 直接读写；密码会随整段 JSON 明文保存到客户端 | 必须迁移。默认不持久化密码/私钥，服务器详情 API 不返回该类敏感字段 |
| `ssh_folders` | 服务器树目录和父子关系 | 浏览器数据清理即丢失 | 必须迁移 |
| `ssh_history` | 最近 100 条执行命令 | 浏览器数据清理即丢失，且可能包含敏感参数 | 迁移，服务端保留上限仍为 100 条并支持用户清空 |
| `ssh_templates` | 命令模板 | 浏览器数据清理即丢失 | 必须迁移 |
| `ssh_prompt_tree_v2` | 提示词树、设备类型、终端高亮规则 | 浏览器数据清理即丢失 | 必须迁移 |
| `ssh_selected_prompt_ids_v2` | 当前选用的提示词 | 浏览器数据清理即丢失 | 迁移为用户偏好 |
| `ssh_agent_config` | AI 行为配置，可能含 `customKey` | 浏览器数据清理即丢失，`customKey` 不能明文同步 | 迁移非敏感行为配置；`customKey` 继续由环境变量提供，不进入 SQLite |
| `multi-ip-operations` | 多 IP 任务、步骤、目标、命令输出、AI 决策 | Zustand `persist` 保存于 `localStorage`；输出可能敏感 | 仅归档已结束任务；运行中任务不支持跨设备续跑 |

### 2.2 仅存在于内存或明确不持久化的数据

| 数据 | 证据 | 方案决策 |
| --- | --- | --- |
| 日志、批量对比结果、终端会话、连接状态、失败计数 | `useSSHStore.ts` 仅初始化于内存 | 维持内存态，不写配置库 |
| AI 对话会话 | `AIChatPanel.tsx` 初始化时主动删除 `ssh_ai_sessions` | 当前产品明确选择“刷新后为空”；本期不改变。若未来需要审计/知识库，另立需求并定义保留期与脱敏规则 |
| 旧提示词键 `ssh_prompt_profiles` / `ssh_selected_prompt_profile` | 新提示词 Store 有兼容迁移；`Terminal.tsx` 仍会读取旧键 | 迁移完成后统一改为读取后端下发的提示词状态，删除这条遗留读取链路 |

### 2.3 后端现状与缺口

- `back/src/app.module.ts` 当前只装配 SSH 模块；`back/package.json` 未声明 ORM、数据库驱动或认证依赖。
- `back/src/ssh/ssh.gateway.ts` 提供 Socket.io SSH 事件；前端 `sshService.ts` 当前把 IP、用户名和密码作为 `ssh-connect` 事件载荷发送。
- `electron/main.cjs` 已负责启动 NestJS 子进程并可获得 Electron API，但尚未把 `app.getPath('userData')` 传给后端，也没有本机数据库、备份或恢复流程。
- `components/AISSH/types/index.ts` 的 `Server.password` 是可选明文字段，必须在迁移中取消它的持久化语义。

## 3. 方案选择

### 3.1 可选路径

| 路径 | 能否覆盖本机重装不丢失 | 取舍 |
| --- | --- | --- |
| A. `localStorage` | 否 | 当前实现；易丢失且不适合保存敏感配置 |
| B. Electron 用户数据目录中的 SQLite | 是，覆盖安装时保留 | 推荐。单机、轻量、无需外部服务，适合当前产品 |
| C. 远程 PostgreSQL/云同步 | 是，也支持跨设备 | 不属于本期本地化需求；未来有多设备同步需求时再增加，不能替代本机备份 |

**推荐采用 B**：在已有 NestJS 后端增加本机“配置库”模块，使用 Node 22 内置的 `node:sqlite` 与明确的 SQL 迁移。当前 Electron 39 内嵌 Node 22.21，已实际验证 `DatabaseSync` 可读写 SQLite；这避免额外原生依赖、pnpm 重装和 `.node` 绑定的打包风险。`node:sqlite` 在 Node 22 仍标为 experimental，应用启动时需保留明确的能力检查，后续 Electron 升级时复测。

### 3.2 关键安全决策

1. 客户端不再把 SSH 密码、私钥或 AI 自定义密钥写入 `localStorage`；默认不保存 SSH 密码和私钥，继续在连接时临时输入。
2. 若后续需要“记住凭据”，使用系统钥匙串（macOS Keychain、Windows Credential Manager、Linux Secret Service）而不是 SQLite。SQLite 只记录是否已配置凭据及对应的系统钥匙串引用，不保存明文或应用自管密钥。
3. NestJS 本机 API 只绑定 `127.0.0.1`，CORS 仅允许本地 Vite/Electron 来源；不新增账号体系和远程开放端口。
4. SSH 连接逐步改为前端只传 `serverId`，本机后端从 SQLite 读取 host、port、username；未保存凭据时，密码仍作为当前连接的短生命周期参数。
5. 现有前端构建配置会把 OpenAI 环境变量注入浏览器。迁移期间不得把 `AgentConfig.customKey` 写入 SQLite；后续单独处理 AI Key 的后端代理与系统钥匙串存储。

## 4. 目标数据模型

以下是单机 SQLite 逻辑模型；UUID、时间戳由本机后端生成。单机数据库不需要 `users`、登录令牌或 `user_id`。

| 表/资源 | 核心字段 | 说明 |
| --- | --- | --- |
| `schema_migrations` | `version`、`applied_at` | 记录 SQL 迁移版本，启动时顺序执行且只执行一次 |
| `server_folders` | `id`、`name`、`parent_id`、`sort_order`、审计时间 | 目录层级和排序 |
| `servers` | `id`、`folder_id`、`name`、`host`、`port`、`username`、`credential_ref`、审计时间 | 不保存 `status`；`credential_ref` 仅指向系统钥匙串，不含密文 |
| `command_templates` | `id`、`name`、`command`、`description`、`tags_json`、审计时间 | 用户模板 |
| `prompt_nodes` | `id`、`parent_id`、`node_type`、`name`、`sort_order`、`device_type`、`prompt`、`rules_json`、`is_expanded` | 保留现有树形语义 |
| `app_preferences` | `key`、`value_json`、`updated_at` | 保存 selected prompt IDs 与非敏感 AI 行为设置 |
| `command_history` | `id`、`command`、`executed_at` | 最多保留 100 条；新记录去重并淘汰最旧记录 |
| `multi_ip_operation_archives` | `id`、`payload_json`、`status`、`completed_at`、`expires_at` | 只归档 completed/error/cancelled；到期自动清理 |

所有可变资源增加 `updated_at`。本期不做多设备同步，不引入版本冲突协议；未来接入云同步时再增加版本号或 `ETag`。

## 5. API 与前端边界

### 5.1 REST API

| 资源 | 接口 | 行为 |
| --- | --- | --- |
| 全量配置 | `GET /api/v1/configuration` | 返回 SQLite 中的 folders、servers（无密码/私钥）、templates、prompts、preferences、history |
| 服务器/目录 | `POST/PUT/DELETE /api/v1/servers`、`/folders` | 单资源 CRUD；后端校验父子关系、端口与目录循环引用 |
| 凭据引用 | `PUT/DELETE /api/v1/servers/:id/credential-reference` | 本期默认关闭“记住凭据”；开启后仅管理系统钥匙串引用，详情返回 `hasCredential` |
| 模板/提示词 | `POST/PUT/DELETE /api/v1/command-templates`、`/prompt-nodes` | 本机后端保存排序与树关系 |
| 偏好与历史 | `PUT /api/v1/preferences`、`POST/DELETE /api/v1/command-history` | 选择状态、非敏感 AI 设置、最近命令 |
| 多 IP 归档 | `GET/POST/DELETE /api/v1/multi-ip-operation-archives` | 仅结束任务；按保留策略查询和清理 |
| 一次性迁移 | `POST /api/v1/configuration/import-local` | 仅首次或显式执行；SQLite 事务导入，返回规范化配置与错误明细 |
| 本机备份 | `POST /api/v1/maintenance/backup`、`POST /api/v1/maintenance/restore` | 创建 SQLite 一致性快照；恢复前强制创建当前数据库备份 |

### 5.2 Zustand 的职责调整

- Store 仍负责界面即时响应、打开的标签、状态和日志；它不再是长期数据源。
- 新增 `persistenceApi`（或等价服务）封装到本机 NestJS 的请求、错误转换和动态端口获取，不在各 Store 内分散 `fetch`。
- 初始加载顺序：取得本机后端端口 -> 拉取 `configuration` -> 填充 Store -> 用户操作先乐观更新 -> SQLite 写入成功确认；失败时回滚并显示可重试错误。
- 本机后端未启动时，页面不能把内存修改伪称已保存；显示“本地数据服务不可用”并允许重试。离线队列不需要单独设计，因为 SQLite 本身就在本机。

## 6. 数据迁移策略

1. 发布前在测试目录执行 SQL 迁移，验证 `APP_DATA_DIR/data/aissh.sqlite` 由后端创建，且不写入安装目录。
2. 首次启动时先读取 SQLite。若数据库为空且浏览器存在上述键，展示“导入本机配置”的一次性确认。
3. 前端构造导入快照，上传 folders、servers、templates、prompt tree、selected IDs、非敏感 AI 设置、命令历史和已结束多 IP 任务。密码、私钥、`customKey` 不导入；用户在迁移后按需重新输入。
4. 本机后端在一个 SQLite 事务中校验目录树、写入资源、建立旧 ID 到 UUID 的映射，并返回完整规范化配置；任一校验失败时不写入部分数据。
5. 前端以 SQLite 响应覆盖 Store，重新加载后逐项比对数量、树关系、模板和提示词选择状态。迁移成功后保留旧 `localStorage` 30 天作为只读回退副本，不立即清理。
6. SQLite 每次 schema 升级前创建快照，并至少保留最近 7 个每日备份。用户可把备份导出到应用数据目录外的自选路径；恢复前自动备份当前数据库。
7. 30 天后在一次明确的用户确认操作中再删除旧本地键；删除前仍允许导出 JSON。迁移程序必须幂等，重复点击不会生成重复服务器或模板。

## 8. 验收标准

1. 清除浏览器站点数据后，重新打开应用能恢复已迁移的服务器、目录、模板、提示词、选择状态及命令历史。
2. 覆盖安装新版 Electron 应用后，仍能从 `userData/data/aissh.sqlite` 读取同一份配置。
3. 用户主动删除应用数据目录后，能从应用数据目录外的导出备份恢复配置；无备份时界面明确说明数据无法恢复，不作错误承诺。
4. 浏览器 `localStorage`、网络响应、错误日志和 SQLite 数据库中均不存在 SSH 密码、私钥或 AI Key。
5. SQLite 本机 API 不监听局域网接口；运行中 SSH 连接不会在重启后伪恢复；已结束多 IP 任务按照明确保留期可查询。
6. schema 迁移失败或恢复失败时，SQLite 数据保持为操作前状态，且可以从自动备份恢复。

## 9. 待产品确认

1. 凭据策略：是否需要“记住 SSH 密码/私钥”？建议默认不保存；若需要，下一期接入 macOS Keychain/Windows Credential Manager，而不是写入 SQLite。
2. 多 IP 任务和 AI 对话的留存：是否需要审计，分别保留多少天？默认建议多 IP 结束记录 90 天，AI 对话继续不保存。
3. 备份策略：是否默认每天自动备份并保留 7 份，以及是否在设置页提供“导出到自选目录”和“从备份恢复”？
4. 是否仍需要 Web 端独立运行？若需要，Web 模式需另设远程数据库/云同步方案，不能访问 Electron 的本机 SQLite。
